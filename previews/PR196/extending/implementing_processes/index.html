Implementing processes

This page is a step-by-step guide for implementing a new concrete process type in Terrarium. We assume familiarity with the Basic concepts and Core interfaces pages, both of which cover the AbstractProcess interface and variable system. For a concrete, self-contained example that follows the workflow below step by step, see the Implementing a process: 1D linear heat diffusion example.

Control flow

Every process in Terrarium is implemented across three levels of abstraction:

  • I. Top-level interface methods for AbstractProcess, i.e. variables, initialize!, compute_auxiliary!, and compute_tendencies! (see doc section on the AbstractProcess interface)
  • II. Kernel functions; this includes both the @kernel entry point and subsequently inlined functions with signatures of the form compute_*(i,j[,k], grid, fields, ::Process, args...)
  • III. Primitive methods defined directly by the subtype of AbstractProcess. These are scalar-valued, grid-independent functions corresponding to individual terms or expressions in the mathematical formulation of the process physics.

The flow of execution is I → II → III: top-level interface methods are invoked by the enclosing AbstractModel, these methods then launch! their corresponding @kernels which in turn call the inner kernel functions.

Development workflow

We recommend to start implementing new processes using the following workflow:

  1. Start by drafting an initial version of the process struct subtyping AbstractProcess; it's good to start simple by directly putting all relevant parameters into this struct. You can later consider grouping these parameters into logical parameterization types.
  2. Define variables(::Process) for the new process type. Identify which variables are prognostic, which are auxiliary, and which might be assumed to be inputs, provided either by external forcing data or by another process.
  3. Write down unit tests and initial implementations of the the scalar-valued process methods (level III). These should correspond to the key equations or terms in the mathematical formulation of the physics. Note that these methods are invoked on each elementary volume and thus cannot be used to define equations involving spatial gradients or fluxes.
  4. Implement the compute_*(i, j[, k], grid, fields, ...) kernel functions with the corresponding @kernel entry points compute_auxiliary_kernel! and compute_tendencies_kernel! (level II). Functions which might be independently useful outside of the process interface (e.g. adjust_saturation_profile! in SoilHydrology) can also define their own @kernel entry points.
  5. Finally, write implement the top-level process methods for initialize!, compute_auxiliary! and compute_tendencies! that launch! their respective @kernels (level I).

As mentioned above, see the example Implementing a process: 1D linear heat diffusion for a detailed walkthrough of this workflow.

Enabling implicit timestepping

By default, all prognostic variables are integrated explicitly. A diffusion-like operator can instead be integrated implicitly under an IMEX timestepper (see Implicit-explicit time stepping). To support this in a process:

  1. Accept a Timestepping argument. Give the process's compute_tendencies! a trailing positional argument timestepping::Timestepping = Explicit() and pass it through the kernel to the kernel functions, which dispatch on Explicit or Implicit. The model obtains the resolved class of a variable with timestepping(state, Val(:name)). See compute_tendencies! of SoilThermodynamics for an example.

  2. Omit the implicit operator under Implicit(). The tendency under Implicit() must contain only the explicitly treated terms (e.g. sources and boundary fluxes). The omitted terms are applied by the implicit sub-stepper. The Explicit() method must remain unchanged so that the process continues to work with explicit timesteppers.

  3. Route the variable. Define timestepping(::AbstractVariable{:name}, ::YourModel, ::AbstractIMEX) = Implicit() for the model that owns the variable.

  4. Provide the implicit operator. The implicit timestepper calls the block query implicit_operator(model, state, names) once on the host with the names of all routed variables when its cache is allocated at initialization, and the model returns one AbstractLinearOperator for all of them. Every model with implicitly routed variables must define this method; the fallback throws an ArgumentError at initialization. To solve the variables one after the other, return a SplitOperator of newly allocated per-variable operators (e.g. a TridiagonalOperator for a vertical diffusion operator) in the order in which they should be solved; a model that couples its variables returns its own operator type instead. For a model built on the soil, the query is forwarded as implicit_operator(model, state, names) → implicit_operator(soil::AbstractSoil, state, grid, names), which orders the names (energy before water) and assembles the SplitOperator from implicit_operator(soil::SoilEnergyWaterCarbon, state, grid, ::Val{name}) → implicit_operator(process, state, grid). These process-level methods also validate the configuration on the host.

  5. Implement the process hooks. The implicit solver (e.g. Picard) owns the iteration and is generic over the operator and the process. On entry to the implicit step, the prognostic field holds u⁺ = uⁿ + Δt G_exp; the implicit timestepper (BackwardEuler) stores the explicit increment Δt G_exp = u⁺ - uⁿ in the explicit_stage of the variable's ImplicitSolverWorkspace in the BackwardEulerCache, resets the prognostic field to uⁿ (for all implicit variables before any of them is solved), and then calls the solver-level implicit_step!(solver, operator, workspaces, state, model, Δt). When the variable is solved, the solver forms its explicit stage u⁺ from its current field and the increment, so the hooks receive u⁺ as before; it then calls, in each iteration, the hooks below with the model, which forwards them to the process that owns the variable in the same way as the query. The hooks dispatch on an Iteration{name, target, final}, which identifies the variable name, the field target that its linear system is solved for, and whether it is the solver's last iteration; its field number holds the 1-based index of the iteration for information only. Their model-level signatures are

    • linearize!(operator, rhs, state, model, explicit_stage, Δt, ::Iteration{name}): fill the lagged coefficients of operator and the right-hand side rhs at the current iterate, where explicit_stage is the field holding u⁺;
    • solve!(target, operator, rhs, Δt): solve the linear system for the field target, which dispatches on the operator type and needs no process-specific method;
    • implicit_update!(state, model, operator, explicit_stage, Δt, ::Iteration{name}): update the prognostic variable from the solution, conservatively, i.e. from the fluxes implied by the operator;
    • implicit_closure!(state, model, ::Iteration{name, target, final}): re-evaluate the closure, where final is true only in the last iteration.

    The target is not a hook: it is the variable of the prognostic variable's closure relation, as given by varname of the closure, or the prognostic variable itself if it has no closure. A closure relation therefore implements varname if its variable can be integrated implicitly (see, e.g., the method for SoilEnergyTemperatureClosure), and the operator is linearized in that variable. If the operator depends on another implicitly integrated variable, the hooks can read that variable from its prognostic field: since the implicit timestepper resets every implicit variable to uⁿ before the first solve, it holds uⁿ if that variable is solved later and uⁿ⁺¹ if it was solved earlier, never the explicit stage. On exit, the prognostic field must hold uⁿ⁺¹, with any closure variables derived from it consistent. The hooks receive the model as an argument rather than the timestepper cache, so the process does not depend on the solver or on the timestepper. See the implementations for SoilThermodynamics and SoilHydrology with RichardsEq for examples.

The implicit operator itself must still be a well-formed continuous-time operator.

Return the implicit operator of the soil prognostic variables names on grid: a SplitOperator of per-variable operators that solves saturation_water_ice before internal_energy, whatever the order of names. The heat step then advects heat with the water flux of the current step (water_flux, see advective_heat_flux) and sees the end-of-step saturation, while the Richards step sees the beginning-of-step temperature and liquid water fraction (the effect of frozen ground on the hydraulic conductivity is lagged by one step). Other names follow in their given order and are rejected by the per-variable fallback.

Terrarium.Iteration — Type
Iteration{name, target, final}(number)

Identifies one iteration of an implicit solver for the prognostic variable name, whose linear system is solved for the field target (the closure variable, e.g. temperature for internal_energy; defaults to name). final is true in the solver's last iteration. All three are type parameters, so hooks dispatch on them. number is the 1-based iteration index, kept for debugging only.

linearize!(

    rhs,
    state,
    grid,
    energy::SoilThermodynamics,
    soil::Terrarium.AbstractSoil,
    constants::PhysicalConstants,
    explicit_energy,
    Δt
)

Linearize the implicit heat operator of the soil internal energy at the current iterate (linearly implicit backward Euler in temperature, conservative update of the internal energy). On entry, explicit_energy holds U⁺ = U⁰ + Δt G_exp, where G_exp contains the flux boundary conditions (e.g. SoilHeatFlux and GeothermalHeatFlux), the diffusive fluxes implied by gradient boundary conditions on temperature, the advective heat fluxes through the boundary faces, and the heat carried by water crossing the boundaries (compute_boundary_advected_heat!), but not the fluxes through the interior faces. This hook

  1. re-evaluates the energy closure, so that temperature and liquid water fraction are consistent with the internal energy and the current saturation (changed by the water step since tⁿ),
  2. evaluates the face conductivity κ (compute_implicit_conductivity!), the regularized apparent heat capacity C_app (compute_implicit_capacity!), and, with water flow, the advective face velocity C_w q from the water_flux of the step (compute_implicit_advective_velocity!), storing them in the face_conductivity, diagonal_coefficient, and face_velocity of operator,
  3. and assembles the right-hand side C_app Tᵐ - Uᵐ + U⁺ of C_app Tᵐ⁺¹ - Δt ∂z(κ ∂z Tᵐ⁺¹) + Δt ∂z(C_w q T_upᵐ⁺¹) = C_app Tᵐ - Uᵐ + U⁺ (compute_implicit_energy_rhs).

implicit_update! then updates the internal energy conservatively: for any number of iterations, the change of column-integrated energy is exactly Δt times the net boundary flux in G_exp.

Terrarium.BackwardEulerCache — Type
struct BackwardEulerCache{NF, US, Operator<:AbstractLinearOperator, Workspaces<:NamedTuple} <: Terrarium.AbstractTimeStepperCache{NF}

Cache for the BackwardEuler timestepper. previous_state and workspaces are NamedTuples keyed by the names of the prognostic variables routed to the implicit sub-stepper: previous_state holds uⁿ of each variable (stored by update_cache!), and workspaces holds the ImplicitSolverWorkspace of each variable (right-hand side, explicit stage, and non-final Iteration label). The target of the label is the closure variable (as given by varname of the closure) if the variable has a closure, and the variable itself otherwise. operator holds the AbstractLinearOperator of all routed variables, as returned by implicit_operator(model, state, names) (e.g. a SplitOperator of one TridiagonalOperator per variable).

Properties:

  • previous_state::Any: Copy of the state uⁿ at the beginning of the step for each implicitly routed prognostic variable, stored by update_cache!

  • operator::AbstractLinearOperator: Linearized implicit operator of all implicitly routed prognostic variables

  • workspaces::NamedTuple: ImplicitSolverWorkspace of each implicitly routed prognostic variable

Terrarium.ImplicitSolverWorkspace — Type
struct ImplicitSolverWorkspace{I<:Terrarium.Iteration, R, E}

Per-variable working data of an implicit step: the right-hand side rhs of the linear system, the explicit_stage (the explicit increment Δt G_exp on entry to implicit_step!, from which the solver forms u⁺ = u⁰ + Δt G_exp at the initial iterate u⁰), and the non-final Iteration label iteration of the variable. Allocated by the implicit timestepper (see BackwardEulerCache). Not exported.

Properties:

  • rhs::Any: Right-hand side of the linear system

  • explicit_stage::Any: Explicit increment Δt G_exp on entry to the step, and the explicit stage u⁺ once the solver has formed it

  • iteration::Terrarium.Iteration: Non-final iteration label of the variable, naming the variable and the target field of its linear system
