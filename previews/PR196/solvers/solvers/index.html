Nonlinear solvers

Overview

Some land processes such as the implicit skin temperature, require solving pointwise nonlinear algebraic equations. To keep the numerics of such routines modular, device-agnostic, and differentiable, Terrarium provides a barebones interface for solving scalar optimization problems consisting of an objective function and a set of interchangeable solvers.

The general problem is to find values of a target field that drives a residual F(x) to zero,

\[F(x) = 0\]

where F is evaluated by mutating the relevant output fields and reading back the residual. The unknown x is stored in the target field, so the same machinery works for any prognostic or auxiliary quantity solved implicitly.

Objective functions

An ObjectiveFunction couples a residual kernel function to the name of the target field it solves for. The residual kernel has the standard kernel-function call signature F(out, indices..., grid, fields, args...) and is expected to write any intermediate fluxes into out and return the scalar residual. An optional derivative function may be supplied when analytic derivatives are available; if omitted, a simple finite-difference approximation is used.

Terrarium.ObjectiveFunction — Type
struct ObjectiveFunction{target, F, DF}

Represents an objective function for nonlinear solvers. The name target refers to the output Field which should updated on each iteration. The objective function should have the signature

func(out, indices..., grid, fields, func_args...; func_kwargs...)

where indices are the grid indices passed to solve! and directly return the scalar residual. If an analytical derivative is provided via dfunc, it should follow the same signature as func and return the derivative of the residual with respect to the target.

Root solvers

RootSolver wraps the root-finding methods provided by RootSolvers.jl (e.g. Newton's method). When the ObjectiveFunction carries no analytic derivative, a finite-difference derivative is formed automatically so that derivative-based methods such as Newton's method can still be used. This is the default solver for the implicit skin temperature, configured by default_skin_temperature_solver.

Wrapper for RootSolvers.jl root-finding methods.

Fixed-point solvers

FixedPointSolver implements a simple fixed-point iteration $x_{n+1} = g(x_n)$. Since the ObjectiveFunction is formulated as a residual r(x), the iterative scheme uses g(x) = x - \alpha r(x) for the fixed-point update. Updates may be under-relaxed by setting $\alpha < 1$ via RelaxationFactor.

Terrarium.FixedPointSolver — Type
struct FixedPointSolver{NF, R}

Fixed-point (Picard) iteration solver. Repeatedly applies the update g(x) = x - F(x), where F is the residual returned by the ObjectiveFunction, optionally under-relaxed via a RelaxationFactor, until the change in the iterate falls below tolerance or max_iterations is reached.

Properties:

  • tolerance: Numerical tolerance of the fixed point iteration

  • relax: Relaxation scheme

  • max_iterations: Maximum number of iterations to run

Implicit solvers

The nonlinear solvers above act pointwise. Implicit time stepping (see Implicit-explicit time stepping) instead requires solving a coupled system along each column. This is split into two parts: implicit solvers, which subtype AbstractImplicitSolver and are held by an implicit timestepper such as BackwardEuler, define the (nonlinear) iteration, and linear operators, which subtype AbstractLinearOperator, define the form of the linearized system and how it is solved. A solver is generic over the operator, and an operator is independent of the solver. The unit of the implicit solve is the set of all variables of a model that are routed to the implicit timestepper: the model provides a single operator for them, which is either a composite of per-variable operators, such as the SplitOperator below, or an operator that couples the variables. A solver implements the solver-level methods implicit_step!(solver, operator, workspaces::NamedTuple, state, model, Δt) for all routed variables and implicit_step!(solver, operator, workspace::ImplicitSolverWorkspace, state, model, Δt) for a single one (see implicit_step!), which contain only its iteration; the bookkeeping of the time step, such as storing the explicit increment and resetting the prognostic fields to the initial iterate, belongs to the implicit timestepper. The per-variable working data are bundled in an ImplicitSolverWorkspace: the right-hand side rhs, the explicit_stage (which holds the explicit increment Δt G_exp on entry and the explicit stage u⁺ once the solver has formed it from the variable's current field), and the Iteration label iteration, which names the variable and the field that its linear system is solved for, as resolved by the implicit timestepper from the variable's closure (see BackwardEuler). The workspaces are passed as a NamedTuple keyed by variable name, so solvers depend on no timestepper type.

Terrarium.ImplicitSolverWorkspace — Type
struct ImplicitSolverWorkspace{I<:Terrarium.Iteration, R, E}

Per-variable working data of an implicit step: the right-hand side rhs of the linear system, the explicit_stage (the explicit increment Δt G_exp on entry to implicit_step!, from which the solver forms u⁺ = u⁰ + Δt G_exp at the initial iterate u⁰), and the non-final Iteration label iteration of the variable. Allocated by the implicit timestepper (see BackwardEulerCache). Not exported.

Properties:

  • rhs::Any: Right-hand side of the linear system

  • explicit_stage::Any: Explicit increment Δt G_exp on entry to the step, and the explicit stage u⁺ once the solver has formed it

  • iteration::Terrarium.Iteration: Non-final iteration label of the variable, naming the variable and the target field of its linear system

Terrarium.AbstractLinearOperator — Type
abstract type AbstractLinearOperator

Base type for the linearized operator of a model's implicitly integrated prognostic variables. An operator owns its working state (coefficient fields and linear solver), is filled by linearize!, and is solved by solve! in each solver iteration. Operators of several variables either compose per-variable operators (e.g. SplitOperator) or couple them. They are allocated by implicit_operator at initialize and stored in the timestepper's cache (e.g. BackwardEulerCache).

Picard solver

Picard solves the implicit system by a sequence of linear solves with lagged coefficients (Picard iteration [2]); with a single iteration, it is the linearly implicit scheme [33] common in land surface models. The default is two iterations (Picard(NF; iterations = 2)). For the operator of a single variable, its solver-level implicit_step! runs a fixed number of iterations, each of which calls the process hooks linearize!, solve!, implicit_update!, and implicit_closure! of the variable (see Enabling implicit timestepping). For a SplitOperator, it runs these iterations for each component in turn. Since each variable forms its explicit stage as its current field plus the explicit increment when it is solved, each component after the first is stepped from the state left by the components solved before it, as in a sequential split: changes that their closures make to its prognostic field (e.g. the heat moved with the water redistributed by the soil hydrology closure) are kept.

Terrarium.Picard — Type
struct Picard <: Terrarium.AbstractImplicitSolver

Picard (lagged-coefficient) solver for the implicit system of a timestepper such as BackwardEuler. Each iteration linearizes the implicit operator of a prognostic variable at the latest iterate (linearize!), solves the linear system for the closure variable (e.g. temperature) with solve!, which dispatches on the AbstractLinearOperator (e.g. a batched tridiagonal solve for a TridiagonalOperator), updates the conserved variable conservatively (implicit_update!), and re-evaluates the closure (implicit_closure!). The solver is generic over the operator; the process-specific parts are the hooks, which the model forwards to the process that owns the variable.

A single iteration (iterations = 1) is the linearly implicit scheme used by most land surface models. The default of two iterations substantially reduces the lagged-coefficient error near freezing fronts and is the minimum recommended for the modified Picard iteration of the Richards equation [2].

Properties:

  • iterations::Int64: Number of Picard iterations (linearizations and linear solves) per implicit step

References

  • [2] Celia et al., Water Resources Research 26, 1483–1496 (1990)

Operator splitting

A SplitOperator holds the operators of several variables in a NamedTuple, in the order in which they are solved. SoilModel and LandModel return a SplitOperator from the block query implicit_operator(model, state, names) that always solves saturation_water_ice before internal_energy, so that the heat step sees the saturation at the end of the step and advects heat with the water flux of the step, while the Richards step sees the temperature and liquid water fraction at its beginning (see Coupling of water and energy). Operator splitting is therefore a choice of the model rather than a property of the timestepper; a model that solves its implicit variables together would return a coupled operator from the same query. SplitOperator is not exported.

Terrarium.SplitOperator — Type
struct SplitOperator{Operators<:NamedTuple} <: AbstractLinearOperator

Composite AbstractLinearOperator for operator splitting: operators holds per-variable operators keyed by prognostic variable name, in solve order. The model sets this order in implicit_operator; e.g. SoilModel and LandModel solve saturation_water_ice before internal_energy. Solvers apply their single-variable iteration to each component in turn (see Picard). Not exported.

julia> grid = ColumnGrid(CPU(), Float64, UniformSpacing(Δz = 0.1, N = 4));

julia> operator = Terrarium.SplitOperator((b = TridiagonalOperator(ground_domain(grid)), a = TridiagonalOperator(ground_domain(grid))));

julia> keys(operator.operators)
(:b, :a)

Properties:

  • operators::NamedTuple: Per-variable operators, keyed by prognostic variable name, in the order in which they are applied

Tridiagonal operator

TridiagonalOperator is the linear operator of vertical diffusion and, optionally, first-order upwind advection. Its systems are solved with Oceananigans' BatchedTridiagonalSolver, which solves one system per column and runs on CPU and GPU. The operator owns the batched solver and the lagged coefficient fields, diagonal_coefficient at cell centers and face_conductivity at cell faces, which are filled by linearize!. The coefficients of the solver are looked up through Oceananigans.Solvers.get_coefficient, for which Terrarium defines methods on three marker structs, ImplicitDiffusionLowerDiagonal, ImplicitDiffusionDiagonal, and ImplicitDiffusionUpperDiagonal. For a diffusion operator with face conductivity $\kappa$ and cell-centered capacity $C$, these evaluate to the coefficients of

\[C_k\, T_k - \frac{\Delta t}{\Delta z_k}\left[ \frac{\kappa_{k+1/2}}{\Delta z_{k+1/2}} (T_{k+1} - T_k) - \frac{\kappa_{k-1/2}}{\Delta z_{k-1/2}} (T_k - T_{k-1}) \right]\,,\]

with no flux through the column boundaries (boundary fluxes are treated explicitly).

If the operator has a face_velocity $u$ (allocated with TridiagonalOperator(grid; advection = true)), the row also contains the divergence $\Delta t\, (F_{k+1/2} - F_{k-1/2}) / \Delta z_k$ of the upwind advective flux $F = u\, T_\text{up}$, where $T_\text{up}$ is the value of the cell below the face for $u > 0$ and of the cell above it otherwise. The velocity is given in units of the capacity times a velocity, e.g. $u = C_\text{w} q$ for the heat carried by the soil water flux $q$. The advective terms add the outflow of each cell to the main diagonal and its inflow to the off-diagonals with a negative sign, so the system remains an M-matrix for any $u$ and the solution obeys a discrete maximum principle. Through the boundary faces, the outflow, whose upwind value is that of the boundary cell itself, is part of the operator, while the inflow must enter through the right-hand side. Without advection, face_velocity is nothing and the advective terms vanish by dispatch.

An operator may in addition treat a linear term $L_k T_k$ implicitly (e.g. a linear sink or a linearized boundary flux), which adds $-\Delta t\, L_k$ to the main diagonal. Its coefficient is given by compute_implicit_linear_coefficient, which an operator specializes via the trailing arguments it passes to solve!; by default it is zero.

Terrarium.TridiagonalOperator — Type
struct TridiagonalOperator{Solver, DiagonalCoefficient, FaceDiffusivity, FaceVelocity} <: AbstractLinearOperator

Batched vertical tridiagonal AbstractLinearOperator for implicit vertical diffusion and, optionally, first-order upwind advection, with one system per column. Row k of the system for the closure variable ϕ reads

C_k ϕ_k - Δt [∂z(κ ∂z ϕ)]_k + Δt [∂z(u ϕ_up)]_k - Δt L_k ϕ_k = rhs_k,

with the lagged capacity C in diagonal_coefficient (e.g. the apparent heat capacity, or ∂θ/∂ψ for Richards flow), the lagged face conductivity κ in face_conductivity (thermal or hydraulic conductivity), the optional advective face velocity u in face_velocity, and the optional linear coefficient L (compute_implicit_linear_coefficient). u is in units of capacity times velocity, so that u ϕ_up is the advective flux; e.g. u = C_w q (W/m²/K) for the heat carried by the water flux q (m/s), with C_w the volumetric heat capacity of water. ϕ_up is the value in the upwind cell of the face, which keeps the system an M-matrix for any u. face_velocity is nothing for operators without advection, and the advective terms then vanish by dispatch (compute_implicit_face_velocity). Diffusive fluxes and advective inflow through the two boundary faces of the column are masked and enter through the right-hand side; advective outflow through the boundary faces (upwind value of the boundary cell itself) is part of the operator, so a boundary cell cannot lose more than its content.

Properties:

  • tridiagonal_solver::Any: Batched tridiagonal solver with ImplicitDiffusion*Diagonal marker coefficients

  • diagonal_coefficient::Any: Lagged capacity C (Center, Center, Center)

  • face_conductivity::Any: Lagged face conductivity κ (Center, Center, Face)

  • face_velocity::Any: Lagged advective face velocity u (Center, Center, Face), or nothing without advection

    soil::Terrarium.AbstractSoil,
    state,
    grid,
    names::Tuple{Vararg{Symbol}}
) -> Terrarium.SplitOperator

Return the implicit operator of the soil prognostic variables names on grid: a SplitOperator of per-variable operators that solves saturation_water_ice before internal_energy, whatever the order of names. The heat step then advects heat with the water flux of the current step (water_flux, see advective_heat_flux) and sees the end-of-step saturation, while the Richards step sees the beginning-of-step temperature and liquid water fraction (the effect of frozen ground on the hydraulic conductivity is lagged by one step). Other names follow in their given order and are rejected by the per-variable fallback.

source
implicit_operator(soil::SoilEnergyWaterCarbon, state, grid, ::Val{name})

Return the implicit operator of the soil prognostic variable name on grid: that of the energy process for internal_energy and of the hydrology process for saturation_water_ice. The fallback throws an ArgumentError.

Interface

Terrarium.solve! — Function
solve!(out, indices, grid, fields, objective_func!::ObjectiveFunction, solver, args...; kwargs...)

Solve the nonlinear problem defined by objective_func! for its target field at the given indices, mutating out in place. The objective returns the residual F(x) whose root is sought; on return, the target field holds the converged estimate and the method returns the root (and, for some solvers, the number of iterations performed). Dispatches on the concrete solver type, e.g. RootSolver, NewtonSolver or FixedPointSolver.
